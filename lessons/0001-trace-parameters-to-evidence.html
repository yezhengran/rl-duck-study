Lesson 0001 · 约 25 分钟

从一个参数，追到它改变的问题和证据

本课的胜利条件不是“记住超参数”，而是拿到任意一个参数后，能回答三句话：它在哪一层？它实际在哪里生效？改后应看到什么证据？

今天的产出：完成一张尚不消耗 GPU 的实验卡，并能向我解释为什么这个实验只改变了一个可归因因素。

1. 先建立因果链，不要先找旋钮

任务定义观测、动作、命令、奖励、终止
数据生成N 个环境各采 24 步
优势估计gamma=.99，lambda=.95
PPO 更新clip、entropy、KL、lr
评估证据曲线、成功率、rollout、视频

这条链决定“改哪里”。想让鸭子执行另一个目标，先改任务层；想验证同一目标下 PPO 是否更新过猛，才看算法层。把奖励和学习率一起改，即使变好也无法知道是谁造成的。

2. 本地先做无 GPU 配置取证

运行下面三条。第一条只列小鸭子任务；第二条展开当前行走任务；第三条验证回报、GAE、KL 调度等纯函数。

uv run python code/inspect_task.py --list

uv run python code/inspect_task.py \
  --task Mjlab-Velocity-Flat-MicroDuck \
  --section overview rewards curriculum algorithm

uv run pytest tests/test_pure_functions.py -q

从输出里找出以下五个事实，并先自己写答案：

  1. 物理步长、decimation 与控制频率之间是什么关系？
  2. 行走任务有多少个 reward term？总 reward 是哪几项构成的？
  3. action_rate_l2 的权重何时从 −0.1 变为 −1.0？
  4. 上游 runner 的 PPO 配方，与自写 train_v3_ppo.py 的核心值是否一致？
  5. 哪一份代码才决定你运行 train_v3_ppo.py 时真正生效的值？
核对答案

物理步长 0.005 s，decimation=4，所以控制周期 0.02 s、频率 50 Hz。行走任务当前 16 个 reward term。action_rate_l2 在 curriculum 中分阶段变化，到 1500×24 个环境控制步时为 −1.0。上游 PPO 配方与自写 PPO 的核心默认值目前对齐；但运行自写脚本时，真正生效的是 train_v3_ppo.py 调用链中的值。

3. 把“本地改—服务器跑”变成可复现实验

Git 在这里不只是传文件，而是实验身份系统。服务器必须跑一个可命名的 commit，不能跑“我记得改过的那份”。

本地：提交明确的一次实验改动

git status --short
git diff --check
uv run pytest tests/test_pure_functions.py -q

# 只 add 这次实验相关文件，不用 git add -A
git add path/to/changed_file.py experiments/EXP-0001-....md
git commit -m "experiment: describe one controlled change"
git push -u origin experiment/ppo-small

服务器：先锁定身份，再运行

git fetch origin
git switch experiment/ppo-small
git pull --ff-only
git rev-parse HEAD

uv sync --frozen
uv run python code/inspect_task.py --section overview algorithm

export RL_DUCK_CKPT_ROOT=/path/to/checkpoints
export RL_DUCK_RESULT_ROOT=/path/to/results
RL_DUCK_NUM_ENVS=256 \
RL_DUCK_MAX_ITERATIONS=10 \
RL_DUCK_SAVE_INTERVAL=5 \
uv run python code/train_v3_ppo.py

这 10 次迭代是管线冒烟：验证依赖、GPU、日志、checkpoint 和路径，不判断“学没学会”。完整训练再恢复任务所需规模和预算。速度行走的课程表到 2000 iterations 仍在改变，过短的 run 不能代表最终任务。

4. 参数要和可证伪预测配对

例如，不要写“试试把 entropy 调大”。应写：

假设：当前策略在步态形成前 entropy 过早下降，探索不足。

唯一改动：entropy_coef: 0.01 → 0.02。

事前预测：相同 seed、task、预算下，前期 entropy 更高；若假设成立，主任务行为出现得更早。若只有 entropy 更高而 rollout 没改善，则不支持假设。

证据：entropy 曲线 + 相同 checkpoint 间隔的确定性 rollout + 相同指令下的视频。reward 只作辅助，因为它可能由正则项变化带动。

当前 metrics.jsonl 只记录总 reward、loss、value loss、policy loss、entropy、KL、mirror loss 和 lr，没有每个 reward term、episode length 或 success rate。因此它还不足以诊断“哪一项奖励被策略利用”。后续课程会先补诊断日志，再系统调奖励。

5. 三个即时检查

MAX_ITERATIONS 直接控制什么？

自写 PPO 的 clip_param 属于哪一层？

判断“reward 上升代表目标行为改善”，哪种证据更可靠？
